### Host submit-return lifetime condition

The original graphics cleanup has a potential host-lifetime race: a retirement worker can observe GPU completion and destroy a submitted command buffer's pool while the render thread is still inside the corresponding native submit call. Vulkan's object lifetime rules allow implementation access throughout the host command, whose duration ends only on return; device completion alone does not remove this obligation. [Object lifetime and command duration](https://docs.vulkan.org/spec/latest/chapters/fundamentals.html#fundamentals-objectmodel-lifetime), [submission access](https://docs.vulkan.org/refpages/latest/refpages/source/vkQueueSubmit2.html).

Pool reuse avoids this destruction path: the worker returns a Java lease, and native reset occurs on the render thread during later acquisition, after submit has returned. Normal compute submission/wait/retirement already run sequentially on the same worker. The race is a code-level possibility, not a captured explanation for the DMA fault. A history sequence around native calls alone cannot prove overlap because the render thread may be descheduled after native return but before recording its return marker. An original-pool control gated on both GPU completion and host submit return would distinguish this lifetime condition from reduced native destruction frequency.

This direct-command-buffer concern does not establish a blanket host-submit lifetime extension for every buffer, image or query pool referenced by recorded commands. The recorded-resource access rules explicitly cover recording and pending execution; no remaining violation for those resources was established solely from retirement preceding host submit return. Gating all graphics retirement on both GPU completion and the corresponding successful native submit return remains a documented diagnostic-control idea, not an implemented production change or an established crash fix.

## Native GPU-AV failure

Both watched clients exited with `0xC0000005`, reading CPU address `0x500` in `VkLayer_khronos_validation.dll!gpuav::CommandBufferSubState::OnCompletion+0x4b`. The stack continues through `gpuav::QueueSubState::Retire`, `vvl::Queue::Retire`, and `vvl::Queue::ThreadFunc`.

Offline inspection of the off-control dump found `RCX=0` at DLL RVA `0x6881eb`. The instruction bytes `48 83 b9 00 05 00 00 00` decode to `cmp qword ptr [rcx+0x500],0`: a null command-buffer substate (`this`) at the initial postprocessing check, rather than a GPU validation report or an invalid mapped-buffer payload. The [available source](../tmp/gpuav_state_trackers.cpp) retrieves the GPU-AV substate during queue retirement before calling `OnCompletion`. A missing substate during retirement is the working hypothesis; its lifecycle cause is unproven.

The available layer source gives a concrete candidate lifecycle path:

- [CommandBuffer::Destroy](../tmp/vvl_cmd_buffer_state.cpp), lines 412–423, holds `WriteLock` only around `ResetCBState`, then destroys and clears `sub_states_` **outside that lock**.
- [QueueSubState::Retire](../tmp/gpuav_state_trackers.cpp), lines 644–653, takes the retained command buffer's `WriteLock`, obtains `SubState`, and calls `OnCompletion` unconditionally. The [SubState helper](../tmp/gpuav_state_trackers.h), lines 199–200, dereferences the returned pointer without checking it.
- `OnCompletion` explicitly anticipates concurrent command-buffer destruction, but its `NeedsPostProcess` check occurs inside the method, after dereferencing `this`. That check cannot handle a missing substate.

This exposes a post-destruction null-substate path and a lock-scope gap consistent with the native dump. **The available source has not been proven to match the installed validation DLL**, and the dump does not establish which destruction call triggered the sequence. The application audit found engine graphics pools retained through their graphics timeline, compute pools destroyed after completion waits, and host pool resets ordered after their prior submissions complete. Those observations establish GPU-completion ordering, not return from the corresponding graphics host submit: original graphics pool destruction can potentially overlap that call, as described above. No such overlap was captured at the fault. Asynchronous layer retirement and the potential application host-lifetime race remain distinct hypotheses; this layer-source finding does not explain `WRITE_INVALID 0x0` when validation is absent.

Earlier [file-only false control](../tmp/gpuav-explicit-control.log) still reported GPU-AV enabled, so it is not evidence that disabling the master failed. The earlier [explicit master-off run](../tmp/gpuav-off-lava.log), dated September 5, sets both `VK_KHRONOS_VALIDATION_GPUAV_ENABLE=false` and `VK_LAYER_GPUAV_ENABLE=false` and exits successfully after 6m10s. Together with the current core-validation success, this implicates the shared GPU-AV retirement path, not specifically RT consistency. The historical master-off run is not a same-build, same-workload paired control.

## Composition implementation-resource ownership correction

The separate [publication audit](../tmp/gpu-investigation/descriptor-publication-audit.md) identified and reproduced a program-resource ownership gap: compositions A and B can both contain registration R, then C removes R. If B retires before an older retained A, the previous implementation released R's resource owner even though A's implementation table still contained its address. This does not require the command-pool host-submit window. No same-frame stale or zero TLAS, geometry-table or light-table publication was established in the audited normal scene path.

[ProgramSession](../packages/engine/src/main/java/dev/comfyfluffy/caustica/engine/program/ProgramSession.java) now gives each compiler candidate and published composition independent shared claims on its registrations and their implementation resources. Failed/discarded candidates release their claims; a published composition releases only its own claims when its backend retirement callback arrives. Registration teardown and channel drainage wait for the final composition claim. A later composition's exclusive resources can retire while an older composition remains live. The change adds no predecessor chain, GPU wait, shader modification or renderer-backend API change.

The A/B/C behavioral regression failed against the saved pre-fix source (`expected 0 releases, actual 1` while A remained retained) and passes after the correction, including B-exclusive release and channel-drain assertions.
